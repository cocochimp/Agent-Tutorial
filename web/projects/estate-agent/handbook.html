20XX.XX – 20XX.XX

项目：房产经纪经营 AI 智能分析与决策平台 —— 面向城市运营、区域经理与门店经营人员，提供自然语言查数、经营漏斗诊断、业务 SOP / 规则问答、异常原因归纳与经营日报生成能力；知识库示例规模约 8.2 万篇文档 / 62 万个 Chunk，接入 6 类业务 Tool，覆盖经营问答、数据查询和多步分析任务。

项目背景：门店经营数据分散在房源、客源、带看、成交、经纪人及运营指标表中，作业规范、指标口径与运营手册又分散在文档知识库。项目将 LLM 定位为“理解与决策层”，通过 RAG、Tool Calling、LangGraph 状态编排与 Verifier，把“哪个门店转化下滑、为什么下滑、应该怎么跟进”这类自然语言问题转化为可审计的数据查询、漏斗分析、知识检索和多步任务执行。

工作内容：

  1. Agent Runtime / 工作流：将知识检索、SQL 查询、异常分析、指标计算、报表生成等能力封装为 6 类 Function Calling Tools，以 LangGraph StateGraph 管理状态、条件边、重试、Checkpoint 与 Human-in-the-loop，在动态决策节点使用 ReAct；在 260 条多步任务评测集上，Tool Selection Accuracy 由 86.8% 提升至 94.1%，端到端 Task Success Rate 由 73.5% 提升至 89.2%，重复 Tool Call 比例由 7.6% 降至 2.1%。
  2. 企业 RAG / 检索优化：构建 Parent-Child Chunk + Metadata/ACL 文档体系，在线采用 Query Rewrite → ACL/Metadata Pre-Filter → Dense + BM25 → RRF → Cross-Encoder Reranker → Authority/Validity → MMR → Dynamic TopK；在 420 条人工标注 Query上，Recall@20 从 79.0% 提升至 94.0%，MRR 从 0.61 提升至 0.78，nDCG@10 从 0.69 提升至 0.84。
  3. Text-to-SQL / 安全查数：引入 Schema Retrieval、指标口径检索、只读账号、表/字段白名单、SQL AST 校验、超时与行数限制，LLM 只生成受约束查询计划，实际统计由数据库/确定性代码完成；在 180 条 SQL Gold Case上 Execution Accuracy 达 90.6%，高风险 SQL 测试集拦截率 100%，无效 SQL 比例由 14.4% 降至 5.0%。
  4. 可信生成 / 幻觉治理：对数字、时间范围、制度条款等关键结论强制绑定 Tool Result / Evidence ID，加入引用一致性校验、事实核查、业务规则校验与低置信度转人工；在 300 条回答评测集上 Faithfulness 由 87.3% 提升至 96.1%，无依据结论率由 6.8% 降至 1.9%。
  5. Evals & Observability / 性能优化：建设约 500 条分层回归用例，覆盖 Query、Retriever、Reranker、Tool、SQL 与 Agent End-to-End；Trace 记录模型/Prompt/检索参数/Tool I/O/错误码/Token/耗时，并通过缓存、上下文裁剪和动态 TopK 将示例复杂任务 P95 延迟由 5.2s 降至 3.8s，平均 Prompt Token 下降约 28%。

核心技术栈：Python、FastAPI（或 Java/Spring Boot）、LangGraph / StateGraph、Function Calling、RAG、Embedding、Vector DB、BM25、RRF、Cross-Encoder Reranker、ACL/Metadata Filter、Text-to-SQL、Redis、Evals、Trace / Observability。

为什么不把“LoRA”放主线

LoRA/SFT 是模型能力定制，但企业 AI 应用大量问题首先不是“模型不会说话”，而是数据拿不到、知识搜不准、工具调错、流程不可靠、结果不可验证。因此本项目把 LoRA 放在高级加分项：面试算法/大模型岗位时再展开；投 AI 应用、研发、后端、数据岗位时，主线仍然成立。

面试定位话术：“我的优势不是只会调一个大模型接口，而是能把 LLM 放进真实业务系统里：前面做任务理解，中间接知识库和工具，后面做校验、权限、日志和评测，让它变成可以被工程系统使用的 AI 能力。”

为什么 ACL 必须在检索层

错误做法：Prompt 约束
先把机密文档检索出来，再在 Prompt 写“不要告诉用户”。此时敏感内容已经进入应用上下文，安全边界太晚。
正确做法：Retrieval-time ACL
文档/Chunk 带 allowed_roles / department / security_level，Retriever 构造 Filter，让无权限 Chunk 根本不进入候选集。

LLM、RAG、Agent、Tool 到底是什么

1. LLM 是什么

白话：LLM 就是一个非常强的“下一词预测器”。你给它上下文，它根据训练得到的概率分布生成后续 Token。它擅长理解语言、归纳、改写、规划，但不知道你公司今天数据库里的真实数据，也不能天然保证每句话都是真的。

面试不要说：“大模型会思考，所以它什么都能做。”
应该说：“LLM 对语言理解和弱结构推理很强，但外部事实、实时数据、精确计算和权限执行要交给检索与工具。”

2. RAG 是什么

RAG = Retrieval-Augmented Generation，检索增强生成。先从企业知识库找材料，再把材料放进 Prompt，让 LLM 基于材料回答。它解决的是“模型不知道公司内部知识 / 知识更新快 / 回答要有出处”。

3. Agent 是什么

Agent = LLM + Tools + State + Loop/Workflow。它不只输出一段文字，还可以决定“下一步该查什么、调什么工具、工具失败后是否重试、是否向用户追问”。

4. Function Calling / Tool Calling 是什么

不是让模型真的去执行函数，而是让模型输出一个受约束的工具调用意图，例如：

{
  "tool": "query_business_metric",
  "arguments": {
    "metric": "showing_to_deal_rate",
    "time_range": "2026-09-23",
    "group_by": "store"
  }
}

后端接到这个 JSON，再真正执行代码。这样模型负责“决定调用谁”，程序负责“执行”。

5. Embedding / 向量数据库是什么

Embedding 把一段文字变成高维向量。语义越接近，向量距离通常越近。向量数据库负责快速寻找“和用户问题最相似的文档块”。

6. Token / Context Window 是什么

模型并不是无限记忆。Prompt、历史对话、检索文档、工具结果都要占 Token。上下文太长会变慢，还可能让模型“注意力分散”。所以要做上下文选择、摘要、压缩和动态注入。

工作一 · 意图理解与结构化输出

🎯 场景复盘 · 一句话同时包含查数、对比、分析、写结论 Query Understanding / Structured Output
业务现场
业务人员习惯直接说：“帮我看看朝阳这个片区最近 7 天带看转成交率为什么掉了，和上周同期比一下，再给个结论。”他们不会按系统字段逐项填写 region、metric、date、compare_to。
遇到问题
第一版直接把整句自然语言传给下游 Agent。结果不同 Tool 对“最近 7 天”“带看转成交率”“朝阳”的理解不一致：SQL Tool 按自然周取数，分析 Tool 却按滚动 7 天；“转化率”有时被映射成咨询转带看，有时被映射成带看转成交，导致同一请求前后口径打架。
怎么定位
我把失败请求按 Trace 拆开看，发现很多错误不是 SQL 算错，而是在最前面的 Query Understanding 已经把时间窗口、经营指标或比较基线抽错，后面模块只是沿用错误参数。
我做了什么
我负责把自然语言入口改成结构化 Task Spec：用 JSON Schema/Pydantic 约束 intent、region、metric、date、compare_to、tasks；补了时间归一化和业务字典映射；对“转化率”这类多义指标加冲突检测，低置信度时触发澄清，而不是让后面的 Tool 自己猜。
为什么这样选
因为问题本质是“模块边界不稳定”，不是模型知识不够。结构化以后，每个 Tool 只消费固定字段，才能做类型校验、权限判断、重试和回归测试。
结果怎么讲
把 Intent Accuracy、Slot F1、JSON Parse Rate 纳入 Query 层评测；同时观察后续 Tool 参数错误是否下降。面试时重点说明：先修入口参数，才能避免错误一路放大到 SQL、RAG 和报告生成。
被追问时
“Prompt Engineering 你具体做了什么？”就讲这个场景：不是写更长 Prompt，而是把 Prompt 当接口协议，规定字段、枚举、正反例和失败策略。
“为什么要结构化输出？”继续讲不同 Tool 对时间和指标理解不一致的真实故障。
1 分钟话术：“我们最开始把用户原话直接往后传，后来 Trace 里发现很多 SQL/RAG 错误其实源头是第一步把时间或指标理解错了。我负责把入口改成结构化 Task Spec，用 Schema、时间归一化、业务字典和低置信澄清把参数固定下来。这样后面的 Tool 不再各自猜用户意思，问题定位和回归测试也简单很多。”
🎯 场景：用户说：“帮我看看朝阳某片区最近 7 天带看转成交率为什么下降，顺便和上周同期比一下，再给我写个简短结论。”一句话里其实包含：查数据、同比/环比、异常原因分析、生成结论四件事。
自然语言→意图识别→实体抽取→任务拆解→结构化 JSON

为什么第一步必须结构化

如果把整句话直接丢给后面所有模块，每个模块都要重新猜“最近 7 天到底是哪段时间、朝阳对应哪个业务区域编码、转化率到底是哪一层漏斗指标”。结构化之后，后面的工具只接固定字段，系统会稳定很多。

示例结构化输出

{
  "intent": "business_anomaly_analysis",
  "entities": {
    "region": "北京-朝阳",
    "metric": "showing_to_deal_rate",
    "date_range": "last_7_days",
    "compare_to": "previous_7_days"
  },
  "tasks": [
    "query_metric",
    "compare_baseline",
    "anomaly_reasoning",
    "generate_summary"
  ],
  "need_clarification": false,
  "confidence": 0.94
}

实现要点

Schema 约束
用 JSON Schema / Pydantic 约束字段类型、枚举和值域。解析失败就重试或回退。
时间归一化
“昨天、上周一、最近三个月”统一转换成绝对日期范围，避免不同工具理解不一致。
歧义澄清
如果用户说“转化率”但系统里有“咨询转带看率/带看转成交率/客源转成交率”，不能瞎猜，必须追问或根据上下文消歧。

面试追问

为什么一定要结构化输出？直接自然语言传给下一个 Agent 不行吗？
自然语言很难做类型校验、权限判断和失败重试；结构化 JSON 可以做 Schema 校验，也方便日志、Trace 和工具路由。我的原则是：模型内部可以自然语言推理，但模块边界尽量结构化。
LLM 抽错字段怎么办？
三层兜底：第一层 Schema 校验；第二层业务字典/枚举校验，例如 region 必须能映射到合法区域 ID；第三层低置信或冲突时向用户澄清。不要靠“再问一次模型”无限重试。
Prompt Engineering 主要做了什么？
不是堆很多“请认真思考”，而是明确角色、任务、输入字段、允许输出格式、边界条件、正反例和失败策略。结构化任务里，好的 Prompt 更像“接口协议”而不是作文提示词。

工作二 · 企业知识库 RAG：从“能搜”做到“搜得准、搜得安全”

🎯 场景复盘 · 搜到了“相关文档”，却不是“当前真正能用的制度” RAG / Hybrid Retrieval / Reranker / ACL
业务现场
区域经理发现某门店带看转成交率异常后，会继续问“按照运营规范应该怎么跟进、哪些动作要检查、指标口径怎么定义”。这些信息不在数据库，而是在制度、手册和历史案例里。
遇到问题
第一版只做 Dense 向量检索。线上/测试里出现三类典型错误：① 用户问SOP 编号或指标编码时向量检索漏掉精确编号；② 旧版运营规范和新版规范语义几乎一样，旧版反而排前；③ TopK 经常是同一章节的重复 Chunk，真正的审批条款被挤掉。
怎么定位
我整理错误 Query，把失败分成“漏召回”和“排序错误”两类，再看 Recall@20、MRR、nDCG。发现SOP 编号/指标编码主要是漏召回问题；新旧版本和适用范围主要是排序与元数据问题。
我做了什么
我负责把检索链路从 Dense Only 改成 Dense + BM25 双路召回，用 RRF 融合；文档切分改为标题感知 + Parent-Child；Chunk 入库补 department、version、valid_time、ACL 等 Metadata；召回后用 Cross-Encoder Reranker 精排，再做 Validity/Authority 与 MMR 去重，最后 Dynamic TopK 控制注入证据数。
为什么这样选
BM25解决制度号、指标编码等精确 token；Dense 解决“预算超了怎么办”这类语义改写；Reranker 负责候选内部精排；Validity/ACL 是确定性业务约束，不能交给相似度；MMR 用来避免 Context 被重复段落占满。
结果怎么讲
420 条人工标注 Query 上，Dense Only 的 Recall@20 为 79.0%，Dense+BM25 后 89.3%，再加 RRF + Rewrite 到 94.0%；加入 Cross-Encoder 后 Recall 基本不变，但 MRR/nDCG 明显提升。这个结果正好能说明“召回”和“排序”是两层问题。
被追问时
“为什么用 BM25？”讲制度编号漏召回。
“为什么要 Reranker？”讲旧版/不适用制度排前。
“为什么 Parent-Child？”讲 Child 命中了条款半句话但缺条件。
“为什么 MMR？”讲 Top10 七条来自同一章节。
“ACL 放哪？”讲财务机密附件不能先检索再靠 Prompt 隐藏。
1 分钟话术：“我们第一版只用向量检索，语义问题能搜到，但制度编号、旧版制度、重复 Chunk 很容易出错。我当时先做错误分类，发现既有 Recall 问题也有 Ranking 问题，所以不是简单换 Embedding。我把链路改成 Dense+BM25→RRF→Reranker，再把版本、有效期、ACL 做成 Metadata 硬过滤，最后用 MMR 和 Dynamic TopK 控 Context。420 条 Gold Query 上 Recall@20 从 79% 做到 94%，排序指标也明显提升。”
🎯 真实业务型场景：用户问“朝阳某门店带看转成交率连续下降，按照运营规范应该怎么跟进？”SQL 只能给出现象和数值；“怎么处理、适用哪些条件、谁审批”存在制度和手册里。RAG 的目标不是“把最像的文档搜出来”这么简单，而是在权限、时效、版本都正确的前提下，把真正能支撑结论的证据召回并排到前面。

二、Chunk：不是固定 500 字切一刀

Child Chunk
较短，负责向量召回，主题更集中；例如制度第 4.2.1 条单独作为 250~450 tokens 的检索块。
Parent Chunk
保留完整条款/章节上下文。Child 命中后回表取 Parent，避免只拿到半句话导致条件缺失。
Overlap
只在跨段逻辑明显时保留少量重叠，不是越大越好。Overlap 太大会制造大量近重复候选。

怎么选 Chunk Size？不是背 512。先按“用户问题粒度”和“制度条款完整性”设初值，再用 Recall@K + 最终 QA 做实验。项目中，固定 800-token 粗切的 Recall@20 为 82.1%，改成标题感知 + Parent-Child 后为 89.5%。

三、Query Understanding：检索前先决定“怎么搜”

Rewrite
“这个要怎么跟进？”结合上一轮补成“朝阳某门店带看转成交率下降的运营跟进流程”，解决指代和残缺 Query。
Decompose
“为什么异常、制度怎么处理、谁审批”拆成数据子任务 + 知识子 Query，避免一个 Query 同时承担多个目标。
Metadata Extraction
抽取部门、制度类型、业务对象、生效日期等结构化字段，交给 Filter 而不是让向量相似度猜。
可选增强：HyDE / Step-back 可以作为“长尾召回补救”，而不是默认每个 Query 都跑。只有口语和文档术语差距很大、基础混合检索仍漏召时再开启，否则会增加延迟和语义漂移风险。

四、ACL / Metadata Filter：权限必须先于内容注入

文档入库时给每个 Chunk 标记 department、allowed_roles、security_level、valid_from、valid_to、version。查询时后端从真实登录态得到用户权限，并构造过滤条件：

user.roles = ["region_manager"]
user.department = "beijing_chaoyang"

retrieval_filter = {
  "allowed_roles": {"$contains_any": user.roles},
  "department": {"$in": [user.department, "public"]},
  "valid_from": {"$lte": query_date},
  "$or": [
    {"valid_to": null},
    {"valid_to": {"$gte": query_date}}
  ]
}

为什么不只做 Post-Filter？如果先 TopK 再删无权文档，可能 20 条里 18 条都被过滤，最后只剩 2 条，召回会塌。更合理的是尽量做 Pre-Filter / 原生 metadata filter；向量库能力有限时再“扩大候选 + Post-Filter”兜底。

五、Dense + BM25：两路召回互补

Dense / Embedding
解决语义改写：“带看后客户没成交怎么办”可以召回“带看后跟进与转化提升规范”。双塔可离线编码文档，在线只编码 Query，ANN 检索速度快。
BM25 / Sparse
解决精确 token：SOP 编号、指标编码、门店编码、业务缩写。向量有时会把“意思像但编号错”的文档推上来，BM25 可以补精确匹配。

为什么用 RRF 融合

Dense 相似度和 BM25 分数不是同一个尺度，直接相加很危险。RRF 只看排名：score(d)=Σ 1/(k+rank_i(d))，常用 k≈60，对不同检索器的分数尺度更鲁棒。需要根据 Query 类型动态偏向某一路时，再考虑归一化加权。

六、Reranker：召回负责“别漏”，精排负责“排准”

Embedding 是 Bi-Encoder：Query 和 Doc 分开编码再算距离，快但交互浅；Reranker 常用 Cross-Encoder：把 [Query, Doc] 一起输入，让模型做深度交互，因此更准但更慢，只适合几十条候选。

阶段候选数（示例）目标主要指标
Dense / BM25各 Top-60尽可能不漏正确证据Recall@K / Hit@K
RRFTop-40融合双路并去重Recall@40
Cross-EncoderTop-10把真正适用制度排到前面MRR / nDCG@10
MMR + Dynamic TopK2~5减少重复和上下文噪声Faithfulness / Token / Latency

七、为什么还要 Authority / Validity / MMR

Authority
同样相关时，公司正式制度 > 部门操作手册 > 历史经验。权威度是业务先验，不完全交给语义分数决定。
Validity
旧制度即使语义再像，只要已失效就不能给当前问题作证据。生效时间和版本是硬约束。
MMR / Dedup
Top-10 可能 7 条都是同一制度的近重复段。MMR 在相关性和多样性之间取平衡，避免 Context 全被重复内容占满。

Dynamic TopK：不是永远 Top-5。比如要求 Reranker 分数 ≥0.62，最多 5 条、至少 2 条；高置信时只给 2~3 条，低置信时宁可触发“证据不足/澄清”也不硬塞低相关文档。

八、一个完整 RAG Case：为什么这条制度最后能排第一

Case · “朝阳某门店带看转成交率下降，按什么运营规范跟进？” Query → ACL → Hybrid → Rerank → Evidence
Rewrite
结合会话补成“朝阳某门店带看转成交率下降的跟进流程、责任人与核查步骤”。
ACL
当前用户是区域经理，只允许 public + beijing_chaoyang + region_manager 可见文档；其他城市内部运营材料在召回前被过滤。
召回
Dense 命中“门店转化率异常诊断流程”，BM25 命中“经纪运营规范 BK-OPS-17”；两路各 Top-60。
融合
RRF 后“BK-OPS-17 v3”进入 Top-3，“v2”虽然相关但 valid_to 已过期。
精排
Cross-Encoder 判断 v3 第 4.2 节与“带看转成交率下降 + 门店 + 跟进”高度匹配，排到第 1。
去重
其余同章节近重复片段被 MMR 去掉，最终注入 v3 §4.2、§4.3 和一条历史案例。
兜底
如果 ACL 后没有足够证据，回答“当前权限范围内未检索到适用制度”，而不是绕过权限扩大检索。

十、高频面试追问

为什么不用纯向量检索？
企业知识里既有自然语言语义，也有制度号、设备码、指标名等精确 token。Dense 擅长同义改写，BM25 擅长字面精确匹配，两路互补。我的 baseline 是 Dense Only，再通过混合召回观察 Recall@K 是否真的提升。
为什么 Reranker 不能扫描全库？
Cross-Encoder 需要每个 Query-Doc 对都跑一次前向，精度高但计算贵；召回阶段先用双塔/倒排把几万、几十万文档压到几十条，再付得起精排成本。
ACL Filter 放在哪里？为什么不是 Prompt？
放在 Retriever 的查询条件里，由后端 AuthZ 生成。Prompt 只能约束模型行为，不能承担访问控制；无权文档不应该进入候选集和 LLM Context。
Pre-Filter 和 Post-Filter 怎么选？
优先 Pre-Filter，安全边界清晰且不会浪费 TopK；如果向量引擎对复杂 ACL 支持弱，可以扩大召回后 Post-Filter，但必须考虑过滤后候选不足，并设置补召回/兜底。
HyDE 为什么不默认开启？
它能救回“用户问法和文档写法差很远”的长尾 Query，但要额外调用 LLM，会增加成本和延迟，还可能把 Query 改偏。所以先看错误分析：基础 Hybrid Retrieval 仍然漏召的场景才定向开启。
为什么用了 Reranker，Recall@20 还是没变？
这是正常的。Reranker 只改变已经召回候选的顺序，不能创造新候选。它更应该提升 MRR、nDCG 或 Top-3 Hit，而不是粗召回 Recall。

工作三 · Tool Calling 与智能查数：让 AI 真正“做事”

🎯 场景复盘 · 模型能“说出 SQL”，但结果不一定能用于业务 Tool Calling / Text-to-SQL
业务现场
用户会问“过去 7 天各区域能耗同比变化最大的前三个区域是什么？”这类问题要求实时查数据库、按统一口径计算，再解释结果。
遇到问题
早期方案把较完整 Schema 全塞给模型直接生成 SQL，出现过选错同名字段、把同比口径写错、查询扫描范围过大，以及模型拿到 30 多行结果后自己算排名算错的问题。
怎么定位
我把失败分成 Schema 选择错误、SQL 语法/逻辑错误、执行风险、结果计算错误四类。Trace 里同时记录生成 SQL、执行耗时、返回行数和最终回答，才能判断到底是“SQL 错”还是“LLM 解释错”。
我做了什么
我负责增加 Schema Retrieval，只把相关表字段和指标口径给模型；SQL 执行前做 AST 校验、SELECT-only、表/字段白名单、超时和行数限制；数据库用只读账号；同比、排序、聚合等确定性计算交给 SQL/Python，LLM 只解释已经算好的结构化结果。
为什么这样选
Text-to-SQL 最危险的不是“SQL 看起来不优雅”，而是结果错、越权和拖垮数据库。能确定性计算的步骤不应该交给概率生成。
结果怎么讲
180 条 SQL Gold Case 上 Execution Accuracy 达到 90.6%，无效 SQL 比例由 14.4% 降到 5.0%；高风险 SQL 测试集拦截率 100%。重点说明 Gold Case 如何构造、Execution Accuracy 是执行结果是否一致，而不只是 SQL 字符串一样。
被追问时
“Text-to-SQL 最大难点？”从字段歧义、口径、安全和性能四类讲。
“为什么不用模型直接算？”讲 37 个区域排名/同比时模型可能抄错漏行。
“Schema Retrieval 有什么用？”讲全库 Schema 太长且容易选错同名字段。
1 分钟话术：“我们一开始让模型直接基于大 Schema 出 SQL，测试里出现过选错字段和同比算错。我的工作不是只调 Prompt，而是把 SQL Tool 工程化：先检索相关 Schema 和指标口径，再做只读、白名单、AST 校验、超时行数限制；统计和排名交给数据库/Python算。这样模型只负责理解和解释，Execution Accuracy 做到了 90% 以上，高风险 SQL 全部被 Guard 拦住。”
🎯 场景：用户问“过去 7 天朝阳各门店带看转成交率下降最大的前三家门店是什么？”这不是知识问答，答案必须来自经营数据库计算。模型应该决定“查什么”，但真正的统计由 SQL/代码执行。

工具设计原则

LLM：理解用户 → 选择工具 → 填参数
程序：校验参数 → 执行 SQL/API/算法 → 返回结构化结果
LLM：解释工具结果 → 组织成人类语言

一个工具定义示例

{
  "name": "query_metric",
  "description": "查询业务指标，不用于写入数据",
  "parameters": {
    "metric": "string",
    "start_date": "YYYY-MM-DD",
    "end_date": "YYYY-MM-DD",
    "group_by": ["area", "department", "day"],
    "aggregation": ["sum", "avg", "max", "min"]
  }
}

Text-to-SQL 怎么做才像工程项目

Schema Retrieval
先只把相关表/字段给模型，不把整个数据库 Schema 全塞进去。
SQL Guard
只允许 SELECT；禁止 DROP/UPDATE/DELETE；限制表白名单、执行时间、返回行数。
Result Validator
检查空结果、异常值、单位、时间范围，并把 SQL 与结果一起记录到 Trace。

为什么不能让 LLM 直接算

例如数据库返回 37 家门店的带看量、成交量和转化率，LLM 很可能在长上下文里加错、抄错或漏行。正确做法是让 Python/SQL 计算 sum/avg/rank/同比，最后把已经算好的结果交给 LLM 解释。

面试金句：“模型负责理解和决策，确定性程序负责计算和执行；凡是能用代码精确完成的，就尽量不要让 LLM 用概率生成去完成。”

面试追问

Text-to-SQL 最大风险是什么？
一是生成错误 SQL 导致结论错；二是越权读取敏感表；三是生成高成本查询拖垮数据库；四是如果给写权限还可能造成破坏。因此生产上要只读账号、表/字段白名单、SQL 解析校验、超时、行数限制、审计。
用户问了数据库里没有的字段怎么办？
Schema 检索阶段会发现没有对应字段。此时不要编 SQL，返回“缺少数据字段/需要澄清指标口径”，或者路由到知识库查指标定义。
为什么工具返回也要结构化？
因为后续要校验和组合。比如统一返回 {status, data, source, latency, error_code}，Agent 才能知道是“查到了空数据”还是“工具调用失败”。

工作四 · Agent 规划与 LangGraph：ReAct 是“决策”，LangGraph 是“运行时”

🎯 场景复盘 · 多步分析不是固定流水线，中间结果会决定下一步 ReAct / LangGraph / State
业务现场
用户要求“找出昨天成本异常最大的部门，解释原因，查相关制度，再生成一页汇报”。只有第一步 SQL 跑完后，系统才知道下一步应该围绕哪家门店、哪一段经营漏斗继续查。
遇到问题
第一版用一个大 Prompt 让模型一次性规划全部步骤，工具一旦返回空结果/超时，模型容易重复调用同一个 Tool；服务重启后任务从头开始；某些“发通知/创建工单”类动作还存在重复执行风险。
怎么定位
我通过 Trace 统计失败任务的 Tool Sequence，发现主要问题不是模型不会选 Tool，而是状态没有显式管理：不知道上一步到底成功、空结果、超时还是权限拒绝，也没有统一终止条件。
我做了什么
我负责用 LangGraph/StateGraph 把 understand、agent_node、query_sql、rag_search、analyze、validate、human_approval 等做成节点；State 显式保存 tool_results、retry_count、tool_call_count、risk_level；ReAct 只负责动态 next_action；补了重复调用检测、最大步数、错误码路由、Checkpoint 和高风险 Interrupt。
为什么这样选
ReAct 解决“下一步做什么”，LangGraph 解决“怎么可靠地跑”；固定 Workflow 对确定任务更稳，只有路径依赖中间结果时才让 Agent 动态决策。
结果怎么讲
260 条多步任务评测中 Tool Selection Accuracy 86.8%→94.1%，Task Success 73.5%→89.2%，重复 Tool Call 7.6%→2.1%；回答时把提升归因到 Tool Description、Schema、条件路由、错误码与验证节点，而不是笼统说“模型变聪明了”。
被追问时
“ReAct 和 LangGraph 区别？”直接用这个场景说明决策与运行时。
“为什么要 Checkpoint？”讲任务跑到第六步/人工审批时服务重启不能从头来。
“什么时候不用 Agent？”强调固定步骤用 Workflow 更便宜稳定。
1 分钟话术：“这个场景最典型的地方是，下一步依赖上一步结果，所以不能一开始把流程完全写死。我们早期的大 Prompt 版本容易循环、超时后重复调用。我负责把状态显式化，用 LangGraph 管节点、条件边、重试、Checkpoint，ReAct 只在 agent_node 决定下一步。这样把端到端 Task Success 从 73.5% 提到了 89.2%，重复 Tool Call 也明显下降。”
🎯 场景：用户问“找出最近 7 天带看转成交率下降最大的门店，解释原因，查相关运营规范，再生成一页复盘。”路径不是一次就能写死：查完 SQL 后才知道查哪家门店；RAG 可能证据不足；工具会超时；高风险动作可能需要人工审批。这就是为什么既需要 Agent 的动态决策，也需要工程化的状态编排。

一、先把两个概念彻底分开

ReAct：决策策略
Reason/Plan → Action → Observation → 再 Reason。解决“看到当前状态后，下一步调用什么 Tool”。它关心的是Agent 如何决定下一步。
LangGraph / StateGraph：运行时编排
用 Node、Edge、Conditional Edge 和 Shared State 组织步骤，负责重试、循环上限、Checkpoint、人工审批和恢复。它关心的是程序如何可靠地跑完整个过程。
一句话：ReAct 可以运行在 LangGraph 的 agent_node 里；Tool 执行结果写回 State，再回到 agent_node 继续决策。两者不是替代关系。

二、ReAct Loop 到底长什么样

用户目标：找异常门店 → 拆经营漏斗 → 查运营规范 → 写复盘

Reason / Plan:
  先查最近 7 天各门店带看转成交率和历史基线
Action:
  query_metric(date_range=last_7_days, group_by=store)
Observation:
  望京A店带看转成交率 -18.6%，下降最大

Reason / Plan:
  已经知道对象，继续拆客源→带看→成交漏斗及经纪人人效
Action:
  analyze_conversion(store="望京A店")
Observation:
  有效带看 -21.4%，带看后 24h 跟进率 -17.2%

Reason / Plan:
  数据说明“发生了什么”，还要查“运营上应该怎么跟进”
Action:
  retrieve_knowledge(query="望京A店 带看转成交率下降 跟进规范")
Observation:
  命中《门店转化异常诊断与跟进规范 V3》4.2、4.3

Reason / Plan:
  证据齐全 → 进入验证与汇报生成

上面是“逻辑层”的 ReAct：每一步根据 Observation 再决定下一步。

五、Node、Edge、Conditional Edge 怎么理解

概念白话本项目例子
Node一个可执行步骤understand、agent_node、query_sql、rag_search、validate
Edge固定下一步understand → agent_node
Conditional Edge根据 State 决定走哪条边agent_node → SQL/RAG/ask_user/finish
Checkpoint把 State 持久化人工审批前保存，服务重启后继续
Interrupt / HITL暂停自动执行等人工发正式报告、写库、修改配置前审批

六、为什么不是“完全自由 Agent”

生产系统通常用固定主干 + 局部自主决策：理解、鉴权、验证、审批这些关键关卡是确定性 Node；在“下一步需要查 SQL 还是 RAG、要不要补分析”这类开放节点才让 LLM 决策。

方式可控性灵活性适用
固定 Workflow高低步骤确定、规则稳定
自由 ReAct Loop低高探索型任务、低风险场景
混合式 LangGraph + ReAct高中高企业 Agent 主流工程思路

七、怎么防止 Agent 死循环和成本失控

  1. 最大 Tool Call：示例设为 10 次；超过直接进入 fallback。
  2. 重复调用检测：同一 Tool + 相同 canonical arguments 连续出现 2 次，阻断并要求重新规划。
  3. 错误码驱动：TIMEOUT / EMPTY_RESULT / INVALID_ARGUMENT / PERMISSION_DENIED 分开处理，不把所有失败都丢回 LLM 猜。
  4. 预算控制：State 记录 token_budget / tool_budget；低价值循环到阈值后终止。
  5. 高风险操作 Interrupt：写数据库、发通知、执行配置修改等必须暂停等待审批。

九、高频面试追问

ReAct 和 LangGraph 是一个东西吗？
不是。ReAct 是 Agent 的决策范式；LangGraph 是有状态的运行时编排。我的实现里 agent_node 用 ReAct 决定 next_action，LangGraph 负责 State、Tool Node、条件边、重试、Checkpoint 和人工审批。
为什么不用一个超级 Prompt 一次生成？
因为任务依赖外部世界：只有 SQL 返回后才知道下一步查哪个部门；RAG 可能找不到证据；Tool 会失败；审批需要暂停。一次生成不能可靠表达这些状态迁移，也无法做精确错误恢复。
什么时候不用 Agent？
如果步骤完全确定，例如“上传文档→解析→入库”，固定 Workflow 更稳定便宜；如果只是“问文档→回答”，普通 RAG 足够。只有路径依赖中间结果、需要动态选 Tool 时才让 Agent 决策。
Checkpoint 有什么价值？
复杂任务跑到第 6 步或停在人工审批时，不应该服务重启就全部丢失。Checkpoint 保存 State，可以从断点恢复，也便于审计当时模型和工具看到了什么。
为什么 Tool Result 要结构化？
Agent 需要区分空结果、调用失败、权限拒绝、超时等状态；如果 Tool 只返回一句自然语言，很难做条件路由、重试和监控。统一 status/data/source/latency/error_code 更适合工程编排。

工作五 · Context 与 Memory：让多轮对话不断片，又不把历史全塞进去

🎯 场景复盘 · 第二句话只有“它”和“这样”，系统却要知道用户在说什么 Context / Memory
业务现场
上一轮问“朝阳最近 7 天哪家门店带看转成交率下降最大？”，系统回答“望京A店”；下一轮用户直接说“那它上个月也这样吗？”——业务人员不会重新把门店、指标和异常类型说一遍。
遇到问题
早期做法把最近很多轮对话原文全部塞进 Prompt。短对话还能工作，长会话后 Token 越来越高、延迟增加，而且模型偶尔把更早一轮的部门当成“它”的指代对象。
怎么定位
我对长会话错误样本做回放，发现“聊天历史多”并不等于“上下文好”：真正需要的是当前对象、当前指标、时间范围、上轮 Tool Result 这些结构化状态，而不是所有原文。
我做了什么
我负责把上下文拆成 State、短期对话摘要和可选长期记忆三层；当前业务对象和 Tool Result 存结构化 State；最近 N 轮保留原文，更早历史做摘要；只在需要时检索相关历史，并对 Memory 设置作用域、TTL 和权限约束。
为什么这样选
Memory 不是“把聊天记录全存起来”。Agent 恢复、指代消解需要的是结构化且可控的上下文；过量历史会增加成本和噪声。
结果怎么讲
结合 Context 命中率、指代消解准确率、平均 Prompt Token 和 P95 延迟观察效果。项目整体通过上下文裁剪、缓存和 Dynamic TopK，使平均 Prompt Token 下降约 28%，复杂任务 P95 延迟从 5.2s 降到 3.8s。
被追问时
“Memory 和 State 区别？”State 是当前任务确定状态，Memory 是跨轮/跨会话辅助上下文。
“为什么不把所有历史都给模型？”讲 Token、延迟和错误指代三个问题。
🎯 场景：用户先问“朝阳最近 7 天哪家门店带看转成交率下降最大？”系统答“望京A店”。下一句用户只说“那它上个月也这样吗？”——“它”指望京A店，“这样”指同类转化率下滑。

三种“记忆”要分清

类型存什么典型存储用途
会话状态 State当前任务节点、工具结果、对象 ID内存 / Redis / Checkpoint保证流程可恢复
短期对话记忆最近几轮关键上下文、摘要Redis / DB指代消解、多轮追问
长期记忆长期偏好、常用报表、权限内画像DB / 向量库个性化，但必须谨慎

为什么不能把所有聊天记录都塞进去

成本高、延迟高，而且噪声会增加。常见策略是：

  1. 最近 N 轮原文；
  2. 更早历史做摘要；
  3. 只检索和当前问题相关的历史；
  4. 工具大结果不直接全塞，先结构化/聚合。

Context Engineering 是什么

可以把它理解成：在模型有限的上下文窗口里，决定“这一轮到底给模型看什么”。包括系统提示、用户问题、历史摘要、检索证据、工具结果、可用工具描述，甚至不同部分的 Token 预算。

面试区分：Prompt Engineering 更偏“怎么写指令”；Context Engineering 更偏“这一轮给模型装配哪些信息”。

工作六 · 幻觉治理与结果校验：企业 AI 最关键的一层

🎯 场景复盘 · SQL 查对了 18.6%，回答却写成 16.8% Verifier / Hallucination Control
业务现场
系统已经能查数据库、搜制度，但业务方更关心“最终结论能不能信”，尤其是数字、制度条款、时间范围和审批建议。
遇到问题
测试中出现过 Tool Result 是 18.6%，LLM 在长回答里写成 16.8%；也出现过引用了正确制度，但结论其实不被那一段证据直接支持。也就是说“Tool/RAG 对了”不等于“最终回答一定对”。
怎么定位
我把幻觉拆成知识、数据、工具、逻辑、权限几类，分别找可验证信号，而不是用一个笼统的“让模型自检”解决全部问题。
我做了什么
我负责增加 Verifier：关键数字从 Tool Result 结构化字段注入；引用必须绑定 Evidence ID；检查引用是否真正支持结论；校验时间范围、单位、版本和权限；低置信或高风险结论转人工。对于纯确定性规则优先用代码校验，而不是再让 LLM 自评。
为什么这样选
Self-Reflection 本身仍是概率模型，不能替代可确定检查。数字一致性、权限、版本、SQL 执行状态都应该由后端真实结果约束。
结果怎么讲
300 条回答评测上 Faithfulness 87.3%→96.1%，无依据结论率 6.8%→1.9%。面试官追问时要说明 Faithfulness 的判断标准：关键结论是否能被 Evidence/Tool Result 支撑。
被追问时
“你们怎么降低幻觉？”不要只答 RAG，直接讲这个 18.6→16.8 的故障：RAG 解决知识来源，Verifier 解决“回答有没有忠实使用来源”。

所谓“幻觉”不是单一问题。至少要分成下面几类：

幻觉类型例子治理办法
知识幻觉编一条不存在的制度RAG + 引用 + Faithfulness 校验
数据幻觉SQL 查出 18.6%，回答成 16.8%关键数字字段强制从 Tool Result 注入
工具幻觉调用不存在的工具/参数Tool Schema + 白名单 + 参数验证
逻辑幻觉把相关性说成因果规则约束 + 分析模板 + 证据要求
权限幻觉“我已经帮你修改配置”但实际没权限执行状态必须来自后端真实返回

验证链

LLM Draft
  → JSON Schema 校验
  → 数字/字段对齐 Tool Result
  → 引用是否命中证据
  → 业务规则检查
  → 风险级别判断
      ├─ 低风险：直接输出
      ├─ 中风险：Self-Refinement 再生成一次
      └─ 高风险：人工审核

结构化输出为什么重要

例如最终答案先生成：

{
  "conclusion": "朝阳片区转化率下滑主要集中在望京A店",
  "evidence": [
    {"type": "sql", "value": "+23.4%", "query_id": "q_1024"},
    {"type": "rag", "doc": "门店转化异常诊断与跟进规范 V3", "section": "4.2"}
  ],
  "confidence": 0.87,
  "risk": "medium",
  "next_action": "建议复核望京A店有效带看与24小时跟进执行情况"
}

后端可以校验这些字段，再决定怎么渲染，而不是完全相信一段自由文本。

业务现场
单人演示时 Agent 链路能跑通，但接入多人测试后，请求会同时打到 LLM、向量库、数据库和多个业务 Tool，单次任务还可能持续数秒到几十秒。
遇到问题
出现过模型接口超时导致整条链路卡住、Tool 重试造成重复创建、热点 Schema/RAG 查询重复计算、只看最终错误码无法判断是哪一步失败等问题。
怎么定位
我把一次请求拆成 request_id 下的多段 Trace，记录模型、Prompt 版本、检索参数、Tool I/O、SQL、错误码、Token 和耗时，按节点统计 P50/P95 与错误类型。
我做了什么
我参与/负责接入超时与指数退避、备用模型/降级路径、Redis 热点缓存、并发限制；对有副作用 Tool 增加 idempotency_key；长任务增加 Checkpoint；统一 status/data/source/latency/error_code 返回格式，方便条件路由和观测。
为什么这样选
企业 Agent 的问题经常不在“模型回答质量”，而在依赖链路：只要下游任一服务抖动，整个任务都可能失败，所以需要把 AI 调用当成分布式系统的一部分来做。
结果怎么讲
通过缓存、上下文裁剪和 Dynamic TopK，将示例复杂任务 P95 从 5.2s 降至 3.8s，平均 Prompt Token 下降约 28%；同时 Trace 让错误可以定位到 Query/Retriever/Tool/SQL/Generator 的具体层级。
被追问时
“为什么 Trace 比日志重要？”讲一次 Agent 请求内部有多次模型与 Tool 调用。
“幂等怎么做？”讲 Tool 超时重试可能重复创建工单。
“模型挂了怎么办？”讲重试、备用模型和非 AI 降级入口。
API 层
FastAPI / Spring Boot 暴露会话、查询、任务、知识库接口；统一错误码与鉴权。
任务层
长任务异步化，支持状态查询、取消、超时、重试和 Checkpoint。
缓存层
Redis 缓存会话状态、Schema、热点检索结果；注意 TTL 与数据一致性。
权限层
用户身份 → 文档 ACL / 数据范围 / Tool 权限；高风险工具需要审批。
日志与 Trace
记录 request_id、模型调用、Prompt 版本、Tool 参数、耗时、Token、结果状态。
降级与容错
模型超时可切备用模型；RAG 失败时返回“无法确认”而不是编；工具失败返回可解释错误。

幂等是什么，为什么 Agent 里很重要

如果一个工具因为网络超时被 Agent 重试两次，而工具是“创建工单”或“发送通知”，可能重复执行。解决办法：给业务操作带 idempotency_key，服务端检测相同 key 只执行一次。

Checkpoint 是什么

复杂 Agent 跑到第 6 步失败，不应该从第 1 步全部重来。把关键状态持久化：用户问题、已完成节点、Tool Result、审批状态。恢复时从断点继续。

并发和限流

LLM 调用通常比普通 API 慢且贵。需要并发上限、队列、限流、超时、批处理、缓存；否则高峰期容易把模型网关或下游数据库打满。

面试追问

如果模型接口挂了怎么办？
按场景做降级：重试要指数退避；可切备用模型；关键业务可以保留非 AI 的传统查询入口；不能因为模型不可用就让核心业务完全不可用。
为什么 Trace 比普通日志更重要？
Agent 是多步链路。只看最终错误很难定位。Trace 能看到每一步的输入、输出、模型版本、Tool Call、检索结果和耗时，从而判断是意图错、检索错、工具错还是生成错。

评测体系：所有“提升 XX%”都必须能解释怎么算

🎯 场景复盘 · “感觉效果变好了”不能作为上线依据 Evals / Regression / Ablation
业务现场
团队每次改 Prompt、Embedding、Reranker、Tool Description 或 Agent 路由，都可能修好一类问题同时把另一类问题改坏。如果只人工试玩几个问题，很难判断版本是否真的更好。
遇到问题
早期优化经常出现“这几个 Case 好了，但整体不知道有没有退化”；尤其 RAG 的 Recall、排序、最终 Faithfulness 混在一起时，很难知道改动到底影响哪一层。
怎么定位
我把链路按 Query、Retriever、Reranker、ACL、Tool、SQL、Agent E2E、Answer 分层，每层定义 Gold 与指标，不再只看一个最终“正确率”。
我做了什么
我参与/负责建设约 500 条分层回归用例；RAG 用 Gold Evidence 测 Recall@K/MRR/nDCG，Tool 用 Gold Tool/Arguments 测 Selection 与 Arg EM，SQL 用 Gold Result 测 Execution Accuracy，Agent 用验收条件测 Task Success，回答层测 Faithfulness；每次改动做 baseline 对比和 ablation。
为什么这样选
只有分层指标才能判断“是没召回、排错了、工具选错、SQL 算错，还是生成阶段失真”，否则所有问题都只能归咎于“模型不稳定”。
结果怎么讲
面试中任何一个百分比都要能回答四件事：样本哪里来、Gold 怎么标、公式是什么、baseline 是什么。比如 Recall@20=420 条 Query 中 Gold Evidence 进入前 20 的 Query 占比。
被追问时
“94% 怎么测的？”直接说样本数、Gold、TopK 命中定义。
“怎么证明 Reranker 有用？”看 MRR/nDCG，不期待它提升粗召回 Recall。

面试里数字本身不是重点，指标定义、样本来源、Gold 标注、baseline 和实验方法才是重点。没有测量口径的“98%”反而是风险。

我的链路

Step 2
Planning：先查成本明细 → 找异常最大的部门 → 查相关生产/业务指标 → 检索异常处置制度 → 汇总。
Step 3
Tool 1：SQL：按门店汇总最近 7 天带看量、成交量与转化率，并与前 7 天及历史基线比较。返回望京A店转化率下降 18.6%，明显高于其他门店。
Step 4
Tool 2：分析算法：继续拆解房源→客源→带看→成交漏斗，发现有效带看量与带看后24小时跟进率同时下降；统计工具计算相关变化，但不直接把“相关”说成“因果”。
Step 5
RAG：检索“门店转化异常诊断规范”“带看后跟进作业规范”，得到适用的核查步骤、指标口径和跟进要求。
Step 6
Verifier：检查回答中的 23.4% 必须等于 SQL 返回值；检查“应核查生产计划”有制度证据；没有证据的“设备故障”不能下结论，只能写“待核查假设”。

生成：输出“现象 → 数据证据 → 可能原因 → 证据强弱 → 建议动作 → 引用来源”。

高级加分项：知道什么时候该用，比“全部都用”更重要

1. GraphRAG

普通 RAG 擅长“从文档里找相关段落”，GraphRAG 更适合“实体关系很多”的问题，例如“这个异常指标关联哪些设备、部门、制度和历史事件”。但建设图谱成本高，不要为了名词强上。

2. MCP

MCP 可以理解成一种把外部工具/资源以统一协议暴露给模型或 Agent 的方式。面试时重点讲统一工具接入、Schema、权限、可发现性，不要把 MCP 说成“比 Function Calling 更高级的模型能力”。

3. Multi-Agent

可以拆成“数据分析 Agent、知识检索 Agent、报告 Agent”，但多 Agent 会增加通信、上下文、成本和调试难度。简单任务单 Agent + 多 Tool 往往更稳。

4. LoRA / SFT

当 Prompt + RAG + Tool 已经解决不了“稳定输出某种任务格式 / 特定领域行为”时，可以考虑微调。它不是企业知识更新的首选方案，因为知识变化频繁时重新训练成本高。

5. vLLM / 本地部署

如果企业强调数据不出内网、推理成本、吞吐，可以将开源模型通过 vLLM 部署成 OpenAI-compatible API。面试可讲 batch、KV Cache、吞吐与显存，但它是部署能力，不是 Agent 核心。

高频面试追问（建议随机抽题练）

1. 你的项目为什么一定要用 Agent？普通 RAG 不够吗？
普通 RAG 适合“问一个问题 → 找文档 → 回答”。我的场景还包括查数据库、调用分析工具、根据前一步结果决定下一步、失败重试，所以需要 Tool Calling 和状态编排。简单问答仍然走普通 RAG，不强行 Agent 化。
2. RAG 和 Agent 的关系是什么？
RAG 是一种“获取外部知识”的能力，Agent 是“根据目标决定并执行多步行动”的框架。RAG 可以是 Agent 的一个 Tool，也可以单独存在。
3. 为什么不用大模型直接连接数据库然后随便生成 SQL？
风险太高。生产上要做 Schema Retrieval、只读账号、表字段白名单、SQL AST/规则校验、超时、行数限制、审计；复杂指标最好调用预定义数据服务而不是任意 SQL。
4. 你怎么减少幻觉？
先分幻觉类型。知识靠 RAG + 引用；数据靠工具结果；计算靠代码；工具靠 Schema；最终用结构化输出、事实核查、置信度和人工兜底。不是只在 Prompt 里写一句“不要幻觉”。
5. RAG 的 Chunk Size 怎么定？
没有固定魔法值。按文档结构、模型上下文和问题粒度调。通过 Recall@K + 最终 QA 指标做实验。制度文档通常要保持条款完整，并保留标题/父段 metadata。
6. Embedding 和 Reranker 有什么区别？
Embedding 适合大规模快速召回，一次把 query/doc 各自编码；Reranker 对 query-doc 成对深度打分，更准但慢，所以只处理召回后的少量候选。
7. BM25 已经有了，为什么还要向量检索？
BM25 依赖字面匹配，对同义改写弱；向量检索能匹配语义。企业场景既有口语化表达，又有编号/专有名词，所以混合检索互补。
8. 什么是 RRF？
Reciprocal Rank Fusion。它忽略不同检索器的原始分数，只根据排名累加 1/(k+rank)，适合融合 BM25 和向量这种分数量纲不同的结果，简单鲁棒。
9. Agent 为什么会死循环？怎么解决？
模型可能反复调用同一工具或无法判断结束。设置最大步数、重复调用检测、明确终止条件、工具错误码、失败计数和人工兜底。
10. Memory 和 RAG 是一回事吗？
不是。RAG 通常检索企业知识；Memory 更多保存与当前用户/会话相关的历史状态和偏好。实现上都可能用向量检索，但语义和生命周期不同。
11. Prompt 越长越好吗？
不是。太长会增加成本和噪声。应该把稳定规则放系统提示，动态证据按需注入，长历史做摘要，工具描述只给当前可用的。
12. 模型换了，Prompt 需要重新评测吗？
需要。不同模型对指令、JSON、工具调用、长上下文敏感度不同。模型版本、Prompt 版本、检索参数都应该进入回归评测。
13. 如何判断一个问题应该走 RAG 还是 SQL？
问“制度/规则/说明/经验”通常走知识；问“多少/趋势/排名/过去几天”通常走数据；复杂问题可能先 SQL 得到现象，再 RAG 查处理规范。路由可以由意图分类 + 规则共同决定。
14. 如果 RAG 找到多个互相冲突的制度怎么办？
用生效时间、版本、来源权威度和业务范围做冲突消解；无法确定时把冲突明确呈现，不让模型自行选一条“看起来合理”的。
15. 为什么要做 Evals，人工看看不行吗？
人工抽查适合早期，但模型/Prompt/知识库更新频繁，没有自动回归就不知道改一个地方是否把另一个场景搞坏。Evals 是 AI 工程里的单元测试 + 集成测试。
16. Temperature 设多少？
结构化抽取、Tool Calling、SQL 等确定性任务一般低温度；创意文案可更高。但不要把系统稳定性寄托在 Temperature，一个可靠系统还需要 Schema、校验和重试。
17. Context 太长怎么办？
摘要、检索历史、裁剪无关 Tool Result、父子 Chunk、按任务动态分配 Token；必要时把中间结果存状态而不是重复塞 Prompt。
18. MCP 和 Function Calling 有什么区别？
Function Calling 是模型输出结构化工具调用的一种交互方式；MCP 更偏外部工具/资源接入的统一协议与生态。两者可以一起使用，不是简单替代关系。
19. Multi-Agent 一定比单 Agent 好吗？
不一定。多个 Agent 增加通信成本、上下文同步、错误传播和可观测难度。任务边界非常清晰、需要独立角色时才值得拆；否则单 Agent + 多 Tool 更简单。
20. LoRA 在这个项目里什么时候有价值？
当主要问题是模型行为不稳定、固定领域表达/结构任务长期靠 Prompt 很难稳住，且有高质量训练数据时可以考虑。企业动态知识优先 RAG，不应该拿 LoRA 当知识库。
21. 你项目里最难的问题是什么？
建议选“可靠性”而不是单个框架：如何让模型调用正确工具、拿到真实数据、找对知识、失败可恢复、结果可验证。然后用一个具体 Trace 展开。
22. 如果让你重新做一次，你会改什么？
可以回答：更早建立分层评测集和 Trace；减少自由 Agent 路径，更多采用固定主流程 + 局部决策；把权限和数据口径前置，而不是功能做完再补。
23. ACL Filter 和普通 Metadata Filter 有什么区别？
实现上都可能是 metadata 条件，但语义不同：Metadata Filter 主要提升业务相关性/时效性，ACL Filter 是安全边界。ACL 条件必须来自可信登录态和 AuthZ，不能让 LLM 自己生成“我应该有什么权限”。
24. 为什么 LangGraph 图里还会有 ReAct 循环？
LangGraph 管外层 Node/Edge/State；agent_node 内部负责 LLM 决策。Tool 执行后把 Observation 写回 State，再通过边回到 agent_node，所以 ReAct Loop 是图中的局部循环，而 LangGraph 是承载它的运行时。
25. RAG 的 Pre-Filter 会不会伤害 Recall？
会，如果 metadata/ACL 标注错误或 Filter 过紧，会把正确文档在召回前直接删掉。所以权限字段必须高质量；业务 Filter 可做容错/逐步放宽，而 ACL 不能为了 Recall 越权放宽。
26. 你这些提升数字怎么来的？
面试时只讲自己真实测过的数字。做法是固定同一批 Gold 数据，先跑 baseline，再逐步增加模块做 ablation；检索看 Recall/MRR/nDCG，Agent 看 Tool Accuracy/Task Success，生成看 Faithfulness，并记录模型和参数版本保证可复现。

答题易错点：这些话很容易被面试官追死

关于“像真实项目”的数字：面试官最容易追问的是样本量、Gold 标注、baseline、计算公式和失败样例。能解释这些，比写一个夸张百分比更像真项目。
不要说“用了 LangChain 所以实现了 Agent。”
框架不是能力。要讲状态、工具、路由、重试、终止和评测。
不要说“RAG 可以完全解决幻觉。”
RAG 也会检索错、引用错。还要验证、结构化、规则和人工兜底。
不要说“模型自己算同比和排名。”
统计计算交给 SQL/Python，模型只解释。
不要说“准确率 98%”却讲不出评测集。
任何数字都要能解释样本、口径、baseline 和测试方法。
不要说“Multi-Agent 越多越先进。”
企业系统看可靠性，不看角色数量。
不要说“用了 LoRA 就比 RAG 高级。”
它们解决的问题不同。

面试最稳的回答结构：STAR + 技术取舍

S：什么业务场景；T：你要解决什么；A：怎么设计、为什么这么选、失败怎么处理；R：结果怎么评测。技术面最好额外补一句：Trade-off 是什么。
