项目总览 & 30 秒开场

建议背熟的开场：我实习做的是一个机票售后的「退改签 Agent」——用户在订单页问一句「我这票能退吗 / 改到后天补多少钱」，系统要先理解他的诉求、从退改签规则库里找到适用的政策、再调用引擎算出真实差价，并且支持多轮追问。我主要负责把它当成一个「智能体」来搭：从工具编排、意图理解、混合检索、上下文与记忆，到最后的方案生成与质量把关这条完整链路。

先建立一个概念：什么是 RAG，为什么退改签非用它不可

RAG（检索增强生成）＝「先检索、再生成」：不让大模型凭记忆直接答，而是先从可信规则库里检索出适用的退改签政策、从引擎拿到真实差价，再让模型基于这些材料作答。退改签是资金流场景——说错手续费、报错差价就是客诉和资损，模型凭记忆很容易把政策记错、把差价报偏，所以答案必须可溯源、可校验，这正是 RAG 的用武之地。RAG 的两大主力就是后面反复出现的「粗召回（解决召回率，别漏）」和「精排（解决准确率，排准）」。

四个关键词（记住这四个，任何追问都能回到主线）

多源输入理解
用户说的是口语 + 订单里的结构化字段（航司/舱位/票价产品），要先对齐、补全，变成机器能检索的结构化诉求。
检索增强
政策不能靠模型编，必须先从规则库检索到适用条文；差价必须调引擎，不许模型自己算。
记忆增强
多轮咨询要记得上一句，长期要记住这个用户的常航线与退改偏好，本质都是上下文管理。
生成可控
结论必须可溯源、可校验：唯一数据源 + 金额校验 + 政策事实核查，低置信度转人工。

整体架构与检索漏斗

整条链路可以用一句话概括：把一句口语化的退改签诉求，一步步收敛成一条可作答的政策与差价。每一环都是「上一环的输出，下一环的输入」。

用户诉求→意图理解 / 改写→混合召回→精排 / 去重→记忆注入→方案生成→校验

检索漏斗：为什么层层收敛

核心思想是「用便宜的方法多召回，用贵的方法精挑」。候选数量逐层收敛，越往后用的模型越强、越贵，但处理的候选越少（下面的取值与 RAG 实战文档一致：双路 Top-60、融合 Top-40、精排到个位数）：

退改签规则库（各航司/舱位/票价产品文档）
  │  ① 意图理解：1 句诉求 → 1~2 个子诉求（+ 结构化过滤条件）
  ▼
每个子诉求并行两路检索：
  ├─ 语义（向量）检索   取前 60
  └─ 关键词（BM25）检索 取前 60
  │  ② 归一化 + 加权融合（或 RRF）去重 → 前 40   （粗召回出口）
  ▼
③ 精排模型（Cross-Encoder）重排 40 条 → 前 10（动态截断：分≥0.6，最多10，至少2）
  │  ④ 多维度排序 + MMR 去冗余 → 前 5
  ▼
⑤ 注入作答上下文：前 3
一句话记忆：60 → 40 → 10 → 5 → 3。粗召回决定系统效果的上限（漏了就再也找不回），精排只能逼近它、无法超越——所以前面宁可多召回，后面再慢慢精挑。

RAG 核心概念（后面各章的理论底座）

这一章把「机票退改签」用到的检索理论一次讲透，后面工作章节直接引用，不再重复。一句话分工：

1、粗召回解决「召回率（别漏）」
2、精排解决「准确率（排准）」
3、Query 理解在最前面决定「怎么搜」。

一、粗召回：解决召回率问题

北极星：召回侧用双塔（Bi-Encoder）——query 与文档各自离线编码成向量、在线用 ANN 近邻检索，重速度（深度交互太贵，召回阶段付不起）。

核心链路（与实战文档一致）：

输入 Query
  → Filter 过滤（航司/舱位/票价产品等结构化元数据，硬筛选，不打分）
  → Query 扩写（语义 ×3 / 关键字 ×3，救回口语化、残缺、歧义）
  → 双路召回：向量(Top-60，余弦∈[0,1]) ＋ BM25(Top-60，分∈[0,20])
  → Min-Max 归一化 → 加权混合 Final = α·sparse + (1-α)·dense（α≈0.3~0.7）
  → 取前 40 送精排
向量召回（BGE + ANN）
匹配语义而非字面，「我这票能改吗」能召回「Y 舱免费改期规则」；抗同义词、抗改写。弱点：吃不准航司代码、舱位代码、具体票价产品名。
关键字召回（BM25）
基于词频的字面精确匹配：航司代码（MU/CA）、舱位代码（Y/B/M）、票价产品名命中极准，快、便宜、可解释。弱点：完全不懂语义，换个说法就漏召。
Filter 结构化过滤
用订单元数据（航司/舱位/票价产品/出行日期）做硬筛，缩小候选、更快更准；本质是「确定性关卡」，不参与相关性打分。依赖订单字段质量。
QA 子切片（泛化召回）
离线为每篇政策切片用 LLM 生成 3~5 个「用户可能会问的问题」，每个问题独立编码入库并关联父切片 ID。让「问题 vs 问题」而不是「问题 vs 文档」匹配，召回更准。
HyDE（假设性文档）：先让 LLM 对 query「假想写一段答案/相似政策条文」，再用这段假想条文去做向量召回——因为「答案 vs 答案」的向量比「问题 vs 答案」更接近。属于 Query 扩写的一种，专治「用户问法和规则文档写法差很远」。

二、精排 / 重排：解决准确率问题

北极星：精排侧用交叉编码器（Cross-Encoder）——把 query 和 doc 拼在一起在线逐对打分，重精度（候选量已经很小，付得起）。链路：query + doc[Top-40] → 精/重排 → Top 2~10 → 组装 context → LLM。

多维度排序：相关性只是一维

权威度
维护来源表给每种 source_type 一个 [0,1] 先验权重（航司官方 1.0 > 携程规则库 0.8 > 代理说明 0.5 > 转载 0.2），入库打标、精排查表。
时效性
用衰减因子建模：越新规则分越高，但平滑递减（新政策 1.0、半年前≈0.9、一年前≈0.81），不一票否决稍旧但仍生效的规则。
质量分
离线预计算 quality = α₁·完整性 + α₂·准确性 + α₃·可读性。
丰富度（MMR）
贪心地每次选「既相关、又和已选不相似」的一条，去冗余（见下）。
动态截断（代替固定 Top-K）：不再死取 Top-5，而是「取 Final 分 ≥ 0.6 的候选，最多 10 条、至少保 2 条」——高置信时多给、低置信时宁缺毋滥。

三、Query 理解：三大块

① 改写与拆解
上下文改写（「那退票呢」→ 补成完整诉求）、纠错顺句、一句话多诉求拆解（又退又改拆成多条子 query）、扩写（HyDE / 同义变体）。
② 问题理解（只决策不检索）
判是改签还是退票 → 路由到对应规则库；判时效态度 → 要不要加生效日期过滤；判偏精确还是偏语义 → 调融合权重 α。
③ 关键信息提取
把散落属性抽成结构化实体 {航司,舱位,票价产品,出行日期} 喂 Filter；时间归一化「下周」→ 具体日期段。

四、融合方法之辩：RRF vs 加权归一化（面试会追）

方法怎么算优点短板 / 适用
加权归一化各路分数先 Min-Max 归一化，再 Final=α·sparse+(1-α)·dense保留分数「强弱」信息，可按 query 特性调 α需可靠归一化；min/max 受异常值影响，需调 α
RRF只看排名：score = Σ 1/(k + rank)，k 常取 60无需归一化、对异构分数鲁棒，工程简单丢弃分数强度信息；适合分数不可比/难归一化时
本项目选型：退改签两路分数量纲差异大且波动，优先用 RRF 保稳（鲁棒、少调参）；当需要按「这条规则偏精确 / 偏语义」动态调侧重时，再切到加权归一化 + 动态 α。两者不是二选一的对错，而是「稳 vs 细」的取舍。

工作一 · Agent 工具编排与流程规划

🎯 真实需求场景：用户在订单页发一句「帮我看下这票现在啥情况，能改到后天吗，补多少钱」。这件事没法用一条写死的流程搞定：有的票不能改、有的要先查航班状态、用户没说改到哪天还要追问。于是需要让系统像人一样「自己决定下一步调用哪个工具」，这就是 Agent 编排要解决的问题。
用户输入→模型规划下一步→调用工具→看结果再规划→直到给出答案

我做了什么

工具封装
把查航班状态、算退改差价、规则库检索、方案生成、出票封装成统一可调用工具，入参出参用固定 Schema 约束。
多步规划（ReAct）
让模型「思考 → 行动 → 观察结果 → 再思考」循环，自主决定调用哪个工具、按什么顺序调。
流程编排（LangGraph）
用状态机把「解析 → 检索 → 确认 → 生成 → 校验」串起来，关键节点设置置信度阈值和人工兜底。

为什么这么做 + 关键设计

做法为什么参数 / 指标
工具入参出参强制 Schema模型经常传错字段、漏参数，不约束就会调用失败或答非所问。Schema 校验 + 错误重试，工具调用准确率提升至 92%。
强制先检索再作答不强制的话模型会「跳过规则库直接编政策」，这是幻觉的主要来源。规则检索工具设为必经节点。
用状态机而非一条链查不到政策要回退重试、低置信度要转人工、出票要用户确认——固定链路表达不了这些分支。关键节点置信度阈值 + human-in-the-loop。

面试追问

ReAct 和「写死的流程（workflow）」有什么区别？
写死的 workflow 是固定顺序，适合流程确定的场景；ReAct 让模型每一步看着上一步的结果，自己决定下一步做什么，适合「一句话里又想退又想改、要不要追问日期、调哪个工具」这种不确定分支。代价是更耗 token、也更难预测，所以我用状态机把边界框住，只在需要判断的节点交给模型。
为什么工具要做 Schema 约束？不约束会怎样？
模型输出是自然语言概率分布，不约束就可能传错类型、漏字段、编造不存在的参数，导致查错航班、算错差价。用固定 Schema + 校验 + 失败重试，能把工具调用准确率显著拉高到 92%。
不要说「Agent 就是让大模型自动干活。」
应该说Agent 是「模型做大脑 + 工具做手脚 + 编排框边界」，我负责把工具和编排这层做稳。
不要说「流程我用 if-else 串起来的。」
应该说用状态机编排，把重试、转人工、出票确认这些分支显式表达出来。

工作二 · 意图理解与 Query 改写

🎯 真实需求场景：两个真实痛点——① 用户咨询完改签紧接着问「那退票呢，手续费多少」，「退票」到底指退哪张？② 一句话里塞了俩诉求「这票太贵了我想退，要不你看看改签到明天划不划算」。如果不先把诉求「读懂、拆清、补全」，后面检索再强也白搭，因为送进去的 query 本身就是残缺的。
口语诉求→订单字段对齐→诉求拆解→指代消解 / 补全→关键信息提取→结构化诉求

我做了什么（对应 RAG 的 Query 理解三大块）

改写与拆解
一句话多诉求拆成多条子 query；追问做上下文改写与指代消解；必要时 HyDE 扩写、Step-back 政策泛化。
问题理解（决策）
判改签/退票 → 路由规则库；判偏精确/偏语义 → 调融合侧重；判时效 → 要不要加生效日期过滤。
关键信息提取
抽出 {航司, 舱位, 票价产品, 出行日期} 结构化字段，喂给 Filter 硬过滤、喂给精排做加权。

Query 理解的结构化输出（示例）

场景① · 一句话又想退又想改　Query 理解 / 拆解 + 指代消解
场景
用户说：「这票太贵了我想退，要不你看看改签到明天划不划算？」——一句话里既问退票、又问改签比价，且「这票」「它」都依赖当前订单上下文。
处理流程
① 从当前订单对齐出 {航司 MU, 舱位 Y, 票价产品 特价舱, 出行日期}；② 拆成 2 条子 query：「退票手续费规则」「改签到明天差价」各自独立检索；③ 检测到追问里的「它/这票」依赖当前订单，不直接检索，先把订单字段回填进子 query；④ 补全后的完整 query 再走检索与作答。
关键决策
为什么不把退改拼一起检索？——会互相干扰、谁都搜不准。为什么要按诉求拆开？——退票和改签是两套规则、两个工具（退票规则检索 / 差价计算），数据依赖不同，需按依赖顺序求解。
失败兜底
若订单上下文缺失/低置信，补全失败 → 不硬编一个假设，而是提示用户确认是哪张票；指代对象有歧义（多个待出行订单）时，回退为「向用户澄清」。
易踩的坑（语义漂移）：改写不能「过度」。把诉求改得太多会偏离原意反而搜错。所以每次改写都带置信度，低于阈值就回退用原始 query；并用「改写前后一致性」做离线评测，防止改写模块偷偷把召回带坏。

面试追问

为什么不直接把用户这句话丢给大模型，让它一步到位答？
可以做一版基线，但直出有两个问题：一是它「读懂了」不等于「查到了当前订单适用的真实政策」，仍会编；二是一句话多诉求时容易答一半漏一半。所以把「意图理解」和「检索作答」拆开：理解只负责把诉求变成可检索的结构化问题，作答交给检索增强来保证可溯源。
追问里的「那退票呢」你怎么让系统知道指的是哪张票？
靠短期会话记忆做指代消解：把最近几轮对话里出现过的订单对象保留下来，追问时把「这张票/它」绑定到当前订单，再补全成完整 query 去检索。多个候选有歧义时宁可向用户澄清。
什么是 HyDE？退改签里怎么用？
HyDE 是先让 LLM 对问题「假想写一段答案/相似政策条文」，再拿这段去做向量召回，因为「答案 vs 答案」的向量比「问题 vs 答案」更接近。用户问法很口语（「我这票亏了能退点钱不」）和规则文档写法差很远时，用 HyDE 生成一段规范政策条文再检索，能显著提召回。

工作三 · 混合检索与结果精排

🎯 真实需求场景：线上反馈了一个 bug——「用户问『我这经济舱打折票能改吗』，系统搜出来一堆通用退改总则，就是没找到他这张特价舱位适用的那条规则」。排查发现：纯语义检索擅长「意思相近」，但对航司代码、舱位代码、票价产品名这种精确匹配不敏感。于是我加了关键词检索来补这一刀（理论见 RAG 核心概念）。
子问题→语义 60+关键词 60→融合 40→精排 10→去冗余 5→注入 3

我做了什么

双路召回
语义（向量）检索懂「换了说法也能找到」，关键词（BM25）检索懂「航司/舱位代码精确匹配」，两路各取 Top-60 并行互补。
融合排序
两路分数不可比，默认用只看排名的 RRF 融合去重取前 40，再按航司/舱位结构化过滤；需要动态调侧重时切加权归一化。
精排 + 去冗余
用 Cross-Encoder（BGE-Reranker）对 40 条逐条精判取前 10，再用 MMR 去掉近似重复规则取前 5，注入前 3。
场景② · 换个说法的同一条规则　向量召回 vs BM25 谁能命中
场景
用户问的是「我这经济舱打折票，改签到后天要补多少钱」，而规则库里存的是同一条规则的另一种写法「MU 航空 Y 舱特价产品（T fare），改期收取票价差额 + 票面 20% 手续费」。字面几乎不重叠（"经济舱打折票" vs "Y 舱特价产品 T fare"、"改签" vs "改期"）。
处理流程
① 向量召回：能理解「经济舱打折票 ≈ Y 舱特价产品」「改签 ≈ 改期」，语义相近，大概率命中，是这题的主力；② BM25：靠字面，"MU""Y 舱"这些代码仍有部分重叠，作补充；③ 若配合 HyDE（先假想写出规则条文）或 QA 子切片（规则库离线已生成「打折票改期怎么收费」这类问句），命中更稳。
关键决策
这题体现向量召回的价值——跨写法的语义匹配正是 BM25 的盲区；反过来「MU5101 这班」「Y 舱」「T fare」这类精确代码才是 BM25 的主场。所以必须双路都上，靠融合取长补短。
失败兜底
若 embedding 对「舱位代码↔口语」不敏感导致向量也没召回 → 用 QA 子切片泛化召回补救；仍搜不到则判为「无适用规则」，走「不返回错规则，转人工并明确标注'未匹配到您这张票的规则'」，而不是硬塞一条通用总则。
场景③ · 粗召回回来 5 条，精排怎么排　Cross-Encoder + 多维度 + MMR
场景
某条诉求粗召回返回 5 条候选：A、B 是同航司同舱位的近似重复规则（有效期差几天），C 是相邻舱位的规则（B 舱 vs 原 Y 舱），D 是关键词重叠但舱位不对的规则（都含"退票"但是头等舱），E 是真正适用当前订单的那条规则。
处理流程
① Cross-Encoder 逐条把 query 与候选拼一起打分：E 最高、A/B 次之、C 中等、D 因舱位不符被打低分（这正是精排比粗召回强的地方——D 是关键词骗过了 BM25，精排能识破）；② 多维度加权：E 若来自航司官方再加权威度分、A/B 取生效日期最新的；③ MMR 去冗余：A、B 高度相似，只保留其一。
关键决策
最终顺序约为 E > A（或B）> C，D 被过滤、B（与A重复）被 MMR 去掉。C 保留是因为「相邻舱位规则」对解释差异有价值，但排在适用规则之后。λ 取 0.7 偏相关、留一点多样性。
失败兜底
若精排把 D 误判为高分（业务偏移）→ 归因到精排层，注入业务提示词或加难负例重训；若 E 根本没进这 5 条（漏召）→ 不在精排调，回去查粗召回（扩 Top-K / 调融合 / 检查 Filter 是否过紧）。

为什么每层 topK 是这个数

环节取值为什么这么定
每路召回前 60太小（如 20）正确规则可能没进候选，效果上限被锁死；太大后面精排又慢又贵。看 Recall@K 曲线在 50~100 区间收益变平，实战取 60。
融合出口前 40给精排一个「够用又不过量」的候选池；粗召回的目标是「别漏」，精排的目标才是「排准」。
精排出口前 10（动态截断）Cross-Encoder 把问题和候选拼一起联合判断，精度高但很贵。用「分≥0.6、最多10、至少2」动态截断，代替死取 Top-K。
去冗余出口前 5 → 注入 3规则库多近似重复文档，MMR 兼顾相关性与多样性；注入越多噪声越大、成本越高，Top-3 覆盖绝大多数适用规则。
成效：加了关键词检索 + 融合 + 精排后，政策命中率提升 18%，「找不到当前订单适用规则」的问题基本解决。

面试追问

为什么要「向量 + 关键词」两路，只用一路不行吗？
向量检索懂语义、换个说法也能命中（见场景②），但对航司/舱位代码、票价产品名这种精确 token 不敏感；关键词检索正好相反，擅长精确匹配但不懂近义。两者互补，所以做混合检索再融合。
Cross-Encoder 为什么比向量召回准，却不能拿来扫全库？
向量召回是双塔：query 和 doc 各自编码再算距离，没有交互，快但粗。Cross-Encoder 把 query 和 doc 拼一起送进模型做全程自注意力交互，精度高但每一对都要跑一次前向，很贵，只能处理粗召回筛出来的几十条。
融合你用 RRF 还是加权归一化？怎么选？
默认 RRF——只看排名、无需归一化，对两路量纲不一的分数最鲁棒，少调参。当要按「这条规则偏精确还是偏语义」动态调侧重时，改用 Min-Max 归一化 + 加权（Final=α·sparse+(1-α)·dense）。取舍是「稳 vs 细」。

工作四 · 方案生成、幻觉治理与质量把关

🎯 真实需求场景：出过一次线上事故——「模型编造了一条不存在的『航空公司新政策』，还把差价算成了 200 元，实际引擎是 580 元」。退改签是资金流，报错手续费、报偏差价就是客诉和资损。所以这一环的核心不是「答得多漂亮」，而是「可溯源、可校验、错了能拦住」。
检索政策 + 工具差价→约束生成（唯一数据源）→金额 / 政策校验→事实核查→过关 / 自我修正 / 转人工

我做了什么（治幻觉三板斧）

唯一数据源
作答只能引用检索到的政策与工具返回的差价，不许模型自由发挥、凭记忆编政策或自己算钱。
结构化 + 金额校验
强制模型按固定结构输出（是否可改、手续费、政策依据分字段），金额逐项与工具返回比对。
事实核查 + 兜底
对生成结果打置信度，低于阈值触发自我修正重试，仍不过关就转人工，绝不硬输出。

先把幻觉分类，再对症下药

幻觉类型例子主要拦截手段
无中生有编造一条不存在的「航司新规」唯一数据源约束 + 事实核查（比对检索材料里有没有这条依据）
张冠李戴把别的舱位/航司的规则套到这张票唯一数据源 + 精排保证注入的是适用规则（见工作三场景③）

场景④ · 回复里编了个「新规」，金额还对不上　Fact-Checker + Self-Refinement + 金额后验
场景
模型生成的回复里：① 结尾写了「根据航司本月新规，您可以免费改期」——检索材料里根本没这条；② 正文写「只需补 200 元」，但 recalc_change_fee 工具返回的是 580。
处理流程
① 金额后验：正则抽出回复里的「200」，与工具字段 580 比对 → 不一致，标记 quote_mismatch；② 事实核查：把「航司本月新规」拿去和检索命中的政策比对，材料里查无此条 → 标记 unsupported_claim，整体置信度被拉到阈值 0.85 以下；③ Self-Refinement：把「金额必须引用工具的 580、删掉无依据的新规」作为反馈回灌，要求只依据材料重写；④ 重试通过校验后放行。
关键决策
为什么阈值定 0.85？——在评测集上扫阈值看「漏放错误 vs 误拦正确」的 PR 曲线，0.85 是「几乎不漏放硬伤、又不过度误拦」的拐点。为什么金额用代码校验而不是再调个 LLM？——金额比对是确定性问题，代码又快又准，不会跟着幻觉走。
失败兜底
重试上限（如 2 次）防死循环：重试仍不过关 → 不硬输出，转人工客服 / 回复「这条我需要帮您确认下，稍等」。资金流场景宁可不确定，也不能报错价。

为什么这么做 + 关键设计

做法为什么参数 / 指标
唯一数据源约束幻觉的根源是模型「没检索到也硬答」，锁死数据源就锁死大部分幻觉。只允许引用检索政策与工具差价。
金额模板回填 + 后验校验金额是钱，不进模型生成；代码正则抽数与工具字段比对。不一致即重生成，金额绑 tool_call_id 可追溯。
置信度阈值 + 自我修正低置信结果直接给用户风险太高，宁可重试或转人工。阈值 0.85（PR 曲线拐点），重试上限 2 次。
硬规则 + 语义后过滤有些错误（金额、明显矛盾）用规则就能拦，不必都靠模型。规则 + 语义双重把关。
建评测集没有评测集的「优化」都是拍脑袋（详见评测体系章）。分航司/舱位，金标准答案 + 禁止错误类型。
成效：方案正确率提升至 96%，配合缓存与上下文动态注入，单次会话 Token 成本下降约 70%。

面试追问

幻觉是怎么产生的？你怎么治？
幻觉主要来自「模型没有依据也硬答」。先把幻觉分类（无中生有 / 张冠李戴 / 金额错 / 格式错），再三板斧：唯一数据源、结构化输出 + 金额校验、事实核查打置信度低于阈值就自我修正或转人工。资金流场景宁可不答也不能报错价。
Fact-Checker 的置信度阈值怎么定的？
不是拍的。在评测集上扫不同阈值，画「漏放错误率 vs 误拦正确率」的 PR 曲线，取二者平衡的拐点（约 0.85）。阈值调高会拦得更严但误伤正确答案，调低会漏放硬伤，取决于业务对「错答」和「不答」的容忍度。
Self-Refinement 会不会一直重试、卡死？
设重试上限（如 2 次）＋每次都带上「具体哪里错」的结构化反馈。超限仍不过关就转人工或礼貌拒答，绝不无限循环，也绝不硬输出没通过校验的内容。

工作五 · 上下文与记忆系统设计

🎯 真实需求场景：两个需求推动了这块——① 用户会连续追问：「那退票呢」「改到后天呢」，系统必须记得上一轮讲了哪张票、哪个方案；② 用户反复来办退改，产品希望针对他常走的航线和退改偏好给更贴合的话术。前者是「这一轮记得上一轮」（短期），后者是「越用越懂这个用户」（长期）。

记忆系统的三层结构

上下文与记忆系统
├─ 短期记忆（会话级）
│   ├─ 会话状态：当前订单栈（正在办哪张票）、咨询进度（问到第几步）
│   ├─ 多轮指代消解：「那它 / 退票呢」→ 绑定订单栈里的对象
│   └─ 滑动窗口 + 摘要压缩：对话过长时旧内容压成摘要，只留最近几轮原文
├─ 长期记忆（用户级 / 跨会话）
│   ├─ 用户画像：常旅客等级、常出行航线、历史退改偏好、价格敏感度
│   └─ 去重写入：内容做指纹 + 状态锁，避免同一条记忆重复写
└─ 上下文预算管理
    └─ token 有限，按优先级注入：系统提示 > 当前诉求 > 检索政策/差价 > 画像
       （短期会话状态用 Redis 缓存，高频读写又快又省）

三块怎么建（校招够讲的深度）

会话状态（短期）
维护「当前订单栈 + 咨询进度」，让追问能定位到对象；这也是工作二指代消解的数据来源。会话结束即释放。
用户画像（长期）
记录常旅客等级、常走航线、历史退改偏好（更倾向退票还是改签比价）、价格敏感度，向量化存储、检索时作个性化 boost。
预算与回流
画像不是全量塞进上下文，而是按当前订单/航线检索出最相关的几条再注入（画像也当一路「召回」）。历史行为回流成个性化 boost。
画像建模（概念级，不必上重模型）：把它理解成一个随行为累积、随时间衰减的信号即可——常走某航线 → 加权；连续多次问退票 → 标记价格敏感；长期不用 → 缓慢回落。面试讲清「怎么更新、拿它干嘛（驱动话术详略与推荐）」比套公式更重要。
场景⑤ · 一个用户一周内 3 次问同一条航线的退改　画像累积 → 偏好识别 → 个性化话术
场景
同一用户在一周内连续 3 次咨询上海—北京航线的退改，每次都先问退票手续费、再嫌贵，最后问改签差价。
处理流程
① 每次咨询完，把「上海—北京航线、价格敏感、爱比较退改」写入用户画像（做去重写入避免 3 条重复）；② 识别出该用户对价格敏感、在犹豫退还是改；③ 下次再来时，主动同时给出退票费和改签差价两个数，并在话术里直接对比，省得他来回追问。
关键决策
为什么用「多次行为」而不仅「一次」作信号？——偶尔问一次不等于偏好。为什么要主动给对比？——他已经表现出纠结退改，一次性答全比多轮追问体验更好。
失败兜底
样本太少易误判（偶尔手滑 ≠ 偏好）→ 画像更新用平滑/多次确认；画像与作答解耦：即使画像判断错，也只影响话术排序的加权，不会把错的政策当依据（正确性仍由工作四的唯一数据源 + 校验兜底）。

面试追问

对话太长、token 要爆了怎么办？为什么用摘要而不是直接截断？
直接截断会丢掉早期关键信息（比如最初那张票）。用滑动窗口保留最近几轮原文，更早内容让模型压成摘要保留要点，既控 token 又不丢关键上下文；摘要失败还有兜底。再配 token 预算按优先级注入。
用户画像你怎么建模、拿它干嘛？
记录常旅客等级、常走航线、退改偏好、价格敏感度，随行为累积、长期不用缓慢衰减。它驱动两件事：话术（敏感用户主动给退改对比）和检索加权（偏好航线规则优先）。更新要平滑，避免一次波动就误判。
长期记忆会不会把用户的错误答案当依据、导致答错？
不会——画像/记忆只影响话术与加权，不作为作答的数据源。作答的正确性仍由工作四的「唯一数据源 + 金额校验 + 事实核查」保证。两条链路解耦，画像判断错顶多话术不贴，不会答错题。

检索漏斗逐层拆解：每层为什么这么调

架构章讲了「60 → 40 → 10 → 5 → 3」这条漏斗，这一章回答面试官最爱追的问题——每一层的数字、阈值、参数到底怎么来的。核心永远是：在「效果、延迟、成本」之间做权衡，每个参数都能讲清为什么。

① 意图理解层 —— 为什么放在最前面？

为什么做：用户诉求常有「那它/退票呢」这类指代，或一句话塞了多个诉求。不理解就直接检索，等于用一句残缺的话去查规则库，后面召回再强也救不回来——它是投入产出比最高的一层。
拆解
一句话若含多诉求 → 拆成 1~2 个子 query，各自独立走检索。
HyDE
先让模型「假设写一段政策条文」，再拿这段去做向量召回——「条文 vs 条文」的向量比「问题 vs 条文」更接近。
Step-back
把具体诉求抽象成规则维度（如「Y 舱特价票改期」），用于规则召回。
指标：复杂 / 多诉求场景解决率 +25%。改写要设置信度兜底——低置信度就用原始 query，避免「过度改写」导致语义漂移。

② 粗召回层 —— topK 为什么是 60？

为什么两路一起：向量召回懂「语义相近」（换了说法也能找到），但对精确 token（航司/舱位代码、票价产品名）不敏感；BM25 正好相反，擅长精确匹配。两者互补，所以做混合召回。

topK 取值会怎样
太小（如 20）正确规则可能根本没进候选，召回率上限被锁死，后面精排再强也无用。
太大（如 500）Reranker 要逐对打分，延迟和成本线性上涨（Cross-Encoder 很贵）。
60（选它）看 Recall@K 曲线：K 在 50~100 区间收益已趋平（边际递减），实战取 60，是「召回率 vs 成本」的平衡点。
融合两法（详见 RAG 核心概念）：默认 RRF（score = Σ 1/(k + rank)，k≈60，只看排名、最鲁棒）；需要按 query 特性动态调侧重时用 Min-Max 归一化 + 加权（Final=α·sparse+(1-α)·dense，α≈0.3~0.7）。融合去重后取 Top 40。
指标：Recall@40 从 84% → 96%（BM25 + QA 子切片 + Query 改写的累计提升）。记住一句话：粗召回决定系统性能上限，精排只能逼近它、无法超越。

③ 精排 / 重排层 —— 为什么 40 → 10？

为什么需要：粗召回的分数「跨路不可比、噪声多」。Cross-Encoder 把 query 和 doc 拼在一起做全程自注意力交互，判断精度远高于粗召回的「各自编码算余弦」，但很贵——不能扫全库，只能扫粗召回出来的 40 条。
  • 延迟预算：Cross-Encoder 单对约几~十几 ms，40 条可批处理并行，整体控制在端到端 P99（≤1.2s）的预算内；这也是「为什么是 40 而不是 500」的硬约束。
  • 动态截断：不死取 Top-K，而是「Final 分 ≥ 0.6、最多 10、至少 2」，高置信多给、低置信宁缺毋滥。
  • 多维度加权：相关性只是一维，再叠加权威度（航司官方>代理说明）、质量分、时效性（新规则优先），避免「相关但过期/低质」排在前面。
指标：政策 Top-1 命中率 +18%，nDCG@10 +0.12（nDCG 衡量「越相关的排越前」，比单纯命中率更能反映排序质量）。

④ 去冗余（MMR）—— 为什么 10 → 5，λ 怎么定？

为什么做：规则库里有大量「近似重复文档」。若 Top 5 全是同一条规则的不同版本，等于给模型喂了 5 份重复信息，浪费上下文窗口、推高 token 成本。
MMR 每一步选：  argmax [ λ·相关性(d, query) − (1−λ)·max 相似度(d, 已选) ]
λ 取值偏向后果
λ → 1只看相关性退化成普通排序，近似重复规则全进来
λ → 0只看多样性为了不重复把相关性也丢了，可能选进不适用的舱位规则
λ ≈ 0.7相关为主、留一点多样在评测集上扫 λ，看「覆盖率 vs 相关性」，0.7 附近最平衡

N 的消融（示意）：注入 Top-3 已覆盖约 9 成适用规则，Top-5 提升有限却明显增 token，Top-8 几乎不再涨——所以精排留 5、注入 3。

⑤ 生成 + 幻觉治理 —— 为什么只注入 Top 3？

为什么不把 5 条全喂进去：上下文越长，成本越高、噪声越多、越容易被无关内容带偏。经评测，Top 3 已覆盖绝大多数适用规则，性价比最高。
唯一数据源
作答只能引用检索政策与工具差价，不许模型自由发挥。
结构化输出
强制 JSON（是否可改、手续费、政策依据分字段），金额模板回填不进生成。
Fact-Checker
对结果打置信度，阈值 0.85（PR 曲线拐点）——低于就触发 Self-Refinement（重试上限 2 次）或转人工。
指标：方案正确率 ≥ 96%。

⑥ Bad case 归因 —— 出问题先定位在哪一层

面试杀手锏：能按「现象 → 根因层 → 调哪里」定位 bad case，比只会背参数强得多。切忌「哪层出问题都去调精排」。
Bad case 现象根因层调整方向
漏召：适用规则根本没进候选集粗召层回查粗召（扩 Top-K / 调融合权重 / 检查 Filter 是否过紧），别动精排
错排：适用规则在候选里但没进 Top-K精排层提升相关性权重，检查多维特征是否压过了相关性
噪声：Top-K 混入舱位不符的规则精排层压低截断 K 或提高分数阈值，加强难负例训练
冗余：Top-K 几条高度重复重排层调高 MMR 多样性权重（降 λ）
过时：排前的是已失效规则多维度层提升时效权重，检查规则生效日期过滤
业务偏移：某类舱位持续「看似相关实则不对」精排层注入业务提示词或领域微调

评测体系：把「优化」从拍脑袋变成可量化

高频面试追问（点「随机抽题」练手）

Q1：一句话讲清你的项目和你负责的部分。
机票售后的退改签 Agent：用户问能不能退/改、补多少钱，系统理解诉求、从规则库检索适用政策、调引擎算差价、生成清晰解释，支持多轮追问。我负责把它当作一个智能体来搭，覆盖工具编排、意图理解、混合检索、上下文与记忆、方案生成与质量把关这条完整链路。
Q2：为什么要做成 Agent，而不是一个固定流程？
因为分支太多：一句话多诉求要拆、查不到政策要重试、不同舱位要调不同规则、低置信度要转人工。固定流程表达不了这些动态决策，所以用 ReAct 让模型自主规划，再用状态机把边界框住。
Q3：退改签为什么不能只靠大模型直接答？
纯直出有两个硬伤：政策会变、模型记不准；差价是实时算出来的、模型会报偏。退改签是资金流，报错价就是资损。所以把理解与作答拆开——理解把诉求变成可检索的结构化问题，作答交给检索增强 + 引擎工具保证可溯源。
Q4：完整讲一下这条 RAG 链路，60→40→10→5→3 是什么？
双路各召回 Top-60（向量+BM25）→ 融合去重取 40 → Cross-Encoder 精排取 10（动态截断）→ MMR 去冗余取 5 → 注入 3 条给生成。前面便宜多召回保上限，后面贵模型精挑排准。
Q5：向量召回和 BM25 各解决什么？举个例子。
向量懂语义：「经济舱打折票改期」能召回规则库里的「Y 舱特价产品 T fare 改期收费」；BM25 擅长精确匹配：「MU 航司」「Y 舱」「T fare」这类代码。两者互补，用 RRF 融合。
Q6：融合为什么用 RRF？和加权归一化怎么选？
RRF 只看排名、无需归一化，对两路量纲不一的分数最鲁棒、少调参，所以默认用它；当要按 query 偏精确/偏语义动态调侧重时，改用 Min-Max 归一化 + 加权（α）。取舍是「稳 vs 细」。
Q7：Cross-Encoder 为什么准、为什么贵？和双塔啥区别？
双塔（Bi-Encoder）query 和 doc 各自编码再算距离，无交互，快但粗，用于召回；Cross-Encoder 把两者拼一起做全程自注意力交互，精度高但每对都要一次前向，很贵，只能处理粗召回筛出的几十条。
Q8：HyDE、Step-back、QA 子切片分别解决什么？
HyDE：先假想写政策条文再检索，让「条文 vs 条文」更近；Step-back：把具体诉求抽象成规则维度做泛化召回；QA 子切片：离线为规则切片生成「用户可能会问的问题」入库，让「问题 vs 问题」匹配。三者都是提召回。
Q9：MMR 的 λ 怎么定？topK 每层怎么定？
都靠评测集扫参：λ≈0.7（相关为主、留点多样，看覆盖率 vs 相关性曲线）；每路召回 60（Recall@K 拐点）、融合 40、精排动态截断到个位数、注入 3（覆盖率消融）。核心是「效果 vs 延迟成本」权衡。
Q10：多轮对话太长、token 要爆了怎么办？
滑动窗口保留最近几轮原文 + 旧内容压成摘要（不直接截断，免得丢最初那张票），再按 token 预算优先级注入：系统提示 > 当前诉求 > 检索政策/差价 > 画像。
Q11：短期记忆、长期记忆、用户画像是什么关系？
短期是会话级（订单栈+指代消解），解决「记得上一轮」；长期是用户级画像（常航线+退改偏好），解决「越用越懂这个用户」，驱动个性化话术与检索加权。画像随行为累积、随时间衰减。
Q12：幻觉怎么治？置信度阈值 0.85 怎么来的？
先分类（无中生有/张冠李戴/金额错/格式错），再三板斧：唯一数据源、结构化+金额校验、Fact-Checker 打分。阈值在评测集上扫 PR 曲线取「漏放 vs 误拦」平衡拐点，约 0.85；低于阈值触发 Self-Refinement（上限 2 次）或转人工。
Q13：线上出了 bad case，你怎么定位？
按现象归因到层：漏召→查粗召回（别动精排）；错排/噪声→精排；冗余→调 MMR 的 λ；过时→时效权重；某类持续偏→业务提示词或微调。先定位再调，切忌哪出问题都去动精排。
Q14：你怎么证明优化真的有效？
靠带版本的评测集：分层评（Recall@40/nDCG@10/Top-1/端到端正确率），每改一个参数跑一遍对比同版本，线上 bad case 回流补题但发版冻结版本，保证可复现。

答题易错点：面试官很可能继续追

不要说「Agent 就是让大模型自动干活。」
应该说模型做大脑、工具做手脚、编排框边界，我负责工具和编排这层。
不要说「检索就是查数据库。」
应该说是向量 + 关键词双路召回、融合、精排、去冗余的多级漏斗。
不要说「topK / λ 我随便设的。」
应该说在评测集上扫参、看曲线拐点定的，能讲清每个数为什么。
不要说「融合就是把两路分数加起来。」
应该说两路分数不可比，用 RRF 按排名融合（或先归一化再加权）。
不要说「Cross-Encoder 又准就拿它扫全库。」
应该说它逐对交互太贵，只能精排粗召回筛出的几十条，召回得用双塔。
不要说「差价让模型算一下。」
应该说差价只能来自引擎工具，金额走模板回填 + 代码后验校验。
不要说「上下文压缩就是删旧消息。」
应该说滑动窗口保留近几轮 + 旧内容摘要，按 token 预算分优先级。
不要说「模型不会说错，正确率很高。」
应该说用唯一数据源 + 校验 + Fact-Checker 兜底，低置信度宁可转人工。

可以主动反问面试官的问题

  1. 这个岗位偏「智能体应用开发」（搭产品链路），还是偏「算法/数据」（做检索、评测、数据）？我两块都能聊，但想知道侧重点。
  2. 你们的 Agent 更接近固定 workflow 的应用侧，还是通用型 Agent？编排框架是自研还是用 LangGraph 这类？
  3. 线上对「正确率」和「延迟/成本」哪个更敏感？这决定了检索漏斗和模型选型的取舍。

术语速查

术语一句话解释
ReAct让模型「思考→行动→观察→再思考」循环，自主决定调哪个工具。
Function Calling把外部能力（查状态/算差价/查规则）封装成带固定入参出参的工具，供模型按需调用。
RAG（检索增强）先检索真实政策/规则，再让模型基于它作答，减少编造。
Bi-Encoder（双塔）query 和 doc 各自编码成向量再算距离，快，用于召回。
Cross-Encoder（交叉）query 和 doc 拼一起联合打分，准但贵，用于精排。
BM25 / 关键词检索基于词频的精确匹配检索，擅长航司/舱位代码、票价产品名。
RRF 融合只看排名不看分数的融合法（Σ 1/(k+rank)），解决多路分数不可比。
加权归一化融合各路分数 Min-Max 归一化后按 α 加权，保留分数强弱。
HyDE先让 LLM 假想写政策条文，再拿它做向量召回（条文 vs 条文更近）。
Step-back把具体诉求抽象成规则维度，做泛化召回。
QA 子切片离线为规则切片生成「可能被问的问题」入库，问题 vs 问题匹配。
MMR相关性与多样性平衡（λ），去掉近似重复规则。
nDCG@K按位置加权的相关性得分，衡量「越相关越靠前」的排序质量。
指代消解把「那它」「退票呢」还原成它具体指的订单/诉求。
Fact-Checker / Self-Refinement对结果打置信度，低于阈值就自我修正重试或转人工，不硬输出。
Redis缓存高频会话状态/只读数据，降延迟与成本。
